# 运维手册

常规故障的处置路径，全部提炼自仓库在册运维文档（每节末尾标了出处），命令为当时实操验证过的口径。
kubectl 在控制机 `ops-controller`（192.0.2.14）上对集群执行。

## 一、Pod 起不来，查哪里

按这个顺序排查，每步都有对应处置章节：

1. **先看系统监控页**（`/system`）的「异常 Pod」表——命名空间、阶段、原因都在；
   kube-system 也在监控范围内，入口组件卡死看得见。
2. 命令行对账：

```bash
kubectl get pods -A | grep -vE 'Running|Completed'
kubectl -n <命名空间> describe pod <pod名>     # 看 Events
kubectl -n dw-dev get events --sort-by=.lastTimestamp | tail -30
```

3. 按 Events 里的关键词分流：
   - `FailedCreate ... exceeded quota` → 第二节（配额打满）；
   - `ErrImagePull` / `ImagePullBackOff` / 长期 `Pulling` → DEV 无外网，镜像不在节点上：
     第五节（traefik 灌回）或第七节（镜像地址写成 docker.io 的修正）；
   - `MountVolume.SetUp failed ... /tmp/... is not a directory` → 节点重启清了 `/tmp`：
     第三节（SeaTunnel 连接器恢复）；
   - VM 重启后残留 `Unknown` / `Error` / 僵尸 `Terminating` Pod → 幽灵 Pod，`kubectl delete pod` 强删即可。

出处：`docs/运维-异常Pod展示与集群内存优化-20261103.md`、`docs/运维-监控与资源运维-20261024.md` 第七节。

## 二、配额打满怎么办（滚动重建死锁）

**现象**：ResourceQuota `dw-dev-quota` 用量顶到上限（requests.memory 34Gi / limits.cpu 48），
滚动更新时旧 Pod 不退、新 Pod 被 `FailedCreate` 拒绝，页面组件「副本不足」。

**查**：

```bash
kubectl -n dw-dev get resourcequota -o jsonpath='{.items[0].status.used}'
kubectl top nodes    # 配额是「调度账本」，节点真实占用看这个
kubectl top pods -n dw-dev --sort-by=memory | head -20
```

**处置**（2026-11-03 实操口径）：
1. 不动 hard 上限——根因通常是清单按保守大数写死、requests 虚高（当时账面 32.4Gi vs 真实约 15Gi）。
2. 按实测右调削减：那一轮 15 个负载 requests.memory 32.4Gi → 17.7Gi，余 16Gi 滚动空间，
   明细表在 `docs/运维-异常Pod展示与集群内存优化-20261103.md` 第二节。
3. 平台工具：系统监控页 →「右调建议器」，按 Prometheus 7 日 P95×1.3/×2（128Mi 步长）
   出每负载建议，预览后一键应用；三道硬闸兜底（无数据不产建议、应用前校验配额与节点余量、
   JVM 堆与 limit 联动防倒挂）。Flink JM/TM 应用时自动联动 ConfigMap `process.size`。
4. 应急腾位：强删幽灵 Pod；临时缩减非核心负载副本。

**纪律**：资源改动必须「现网 + `deploy/k8s/` 清单 + 代码默认」三处同步，只改一处就是新的漂移；
LimitRange 默认值（1Gi/128Mi）保留，它给同步 Job 类 Pod 兜底。

出处：`docs/运维-异常Pod展示与集群内存优化-20261103.md`、`docs/系统监控-内存右调-20261103.md`。

## 三、/tmp 连接器被清恢复（节点重启后的 SeaTunnel）

**现象**：节点重启后 seatunnel-0/1/2 变 `Error` / `Init:0/1`，Events 报
`hostPath type check failed: /tmp/seatunnel-2.3.13 is not a directory`（发行包和连接器放在节点 `/tmp`，系统会清）。

**正规恢复链（推荐）**：在控制机对重启过的节点跑制品分发，幂等：

```bash
ansible-playbook site.yml --tags artifacts        # 可加 --limit 节点
```

制品在 `deploy/artifacts/seatunnel/*.tgz`，每台重启过的节点各跑一次。

**手工兜底（离线包在控制机时）**：

```bash
sudo mkdir -p /tmp/seatunnel-connectors/jdbc-lib /tmp/seatunnel-2.3.13
scp <dist包> ubuntu@<节点>:/tmp/ && ssh ubuntu@<节点> "sudo tar -xzf /tmp/seatunnel-2.3.13-dist.tar.gz -C /tmp/seatunnel-2.3.13"
```

恢复连接器到**每节点 34 个连接器 jar + 6 个 JDBC 驱动**；
**务必删掉新旧版本重复的 jar**——2.3.9 与 2.3.13 并存时 SeaTunnel 拒绝启动任务
（`Cannot find unique plugin jar for pluginIdentifier: jdbc`）。备份源：控制机 `/d/lab/.work/st-restore`。

然后重建 Pod 并验证：

```bash
kubectl delete pod -n dw-dev seatunnel-0 seatunnel-1 seatunnel-2
kubectl rollout status statefulset/seatunnel -n dw-dev
```

先跑一条 1 行 JDBC 冒烟任务确认插件加载正常，再放量大同步。

出处：`docs/运维-k3s扩容与SeaTunnel恢复-20261020.md` 第二、三节，`docs/运维-异常Pod展示与集群内存优化-20261103.md` 第六节坑 2。

## 四、registry 清理（根盘逼近 85% 前动手）

**为什么**：节点根盘使用率超过约 85% 会触发 kubelet ImageGC，把「不在运行 Pod 引用里」的镜像
删掉——DEV 无外网删不回（曾因此删掉 traefik 镜像导致入口瘫痪，见第五节）。私有仓库数据也在
k8s-node-1 盘上，磁盘告急优先清它。

**查**：

```bash
ssh 192.0.2.11 'df -h /'
```

**清（2026-11-03 实操：26G → 17G，删 104 个过期 tag）**：
1. 保留策略：**最近 10 个版本 tag + 在用 digest**（回滚要点名的版本不能删）；
2. 删过期 tag 后，停 registry 跑 `garbage-collect` 再恢复——不跑 GC 空间不回收；
3. 平台旧版本镜像备份依赖 30500：某版本在 30500 无备份 + 节点本地层缺失时，
   手动回滚会偶发 ErrImagePull（`docs/运维-凭据轮换清单-20261026.md` 已点名此风险）。

**灌镜像的正确姿势**：发布包只拷到一台机器，`bash deploy.sh registry-load` 推进 30500，
节点按需拉；不要逐台 scp。

出处：`docs/运维-异常Pod展示与集群内存优化-20261103.md` 问题 2 与第五节，`deploy/README.md`。

## 五、traefik 镜像灌回（入口组件被 ImageGC 误删）

**现象**：`kube-system/traefik-*` 卡 `ContainerCreating` 几十分钟，Events 长期 `Pulling`
镜像 `rancher/mirrored-library-traefik:3.7.13`——节点上镜像被 ImageGC 删了，外网拉不回；
连带 MCP Ingress（data-ai-agent）不可用。

**处置（2026-11-03 已验证路径）**：
1. 找**还留有该镜像的节点**（当时是 k8s-node-3）导出：

```bash
sudo k3s ctr images export /tmp/traefik.tar rancher/mirrored-library-traefik:3.7.13
scp /tmp/traefik.tar 192.0.2.11:/tmp/   # 缺镜像的节点各一份
```

2. 缺失节点上导入：`sudo k3s ctr images import /tmp/traefik.tar`；
3. 强删卡死 Pod 和僵尸 `Terminating` 旧 Pod，等新 traefik `1/1 Running`，验证 Ingress 恢复。

**防再发**：根盘保持低于 85%（第四节清理）；逼近阈值时优先清 registry 旧 tag。

出处：`docs/运维-异常Pod展示与集群内存优化-20261103.md` 问题 2、第五节第 3 条。

## 六、节点/VM 重启后的例行检查

1. `/tmp/seatunnel-*` 目录还在吗（不在 → 第三节）；
2. `kubectl get pods -A | grep -vE 'Running|Completed'`——幽灵/卡死 Pod 清掉（第一节）；
3. 配额水位：`kubectl -n dw-dev get resourcequota`；
4. 平台自检：`GET /api/health` UP，系统监控页异常 Pod=0、四集群卡全「健康」、16 组件满编；
5. 一条 1 行 JDBC 冒烟同步任务 SUCCESS，再恢复大作业。

出处：`docs/运维-k3s扩容与SeaTunnel恢复-20261020.md` 第三节，`docs/运维-异常Pod展示与集群内存优化-20261103.md` 第六节。

## 七、镜像拉不动的通用根因

`ImagePullBackOff` 在 DEV 基本只有两种原因：
1. **工作负载镜像地址写成了公网地址**（`docker.io/...`）：节点把它转发到镜像站后 403，
   集群没有外网 → 必失败。修法是改回私有仓库地址（如 `192.0.2.11:30500/library/seatunnel:dev`，
   后端同步作业镜像走 `SEATUNNEL_IMAGE` 配置注入）；
2. **镜像根本不在 30500 也不在节点**：从有镜像的节点导出导入（第五节），或 `deploy.sh registry-load` 重灌。

出处：`docs/运维-监控与资源运维-20261024.md` 第七节，`docs/数仓连接路由-20261025.md`，`deploy/README.md`。
